# AGENTS.md

Operating contract for this repository.

The agent writes the code. The human owns the decisions. The human does not read
diffs and does not edit files. Every rule below exists so the human can follow
the project through artifacts, the changelog, and the version history.

A fresh copy is a template until `bootstrap` runs. That skill interviews the
human, fills this file, and chooses the stack. Leave the rest of this contract
alone.

## The loop

Every change runs the same four steps:

```
explore -> propose -> apply -> archive
```

`explore` is optional at L0 and L1 and required at L2 and L3. `propose` writes
the artifacts. `apply` builds and verifies. `archive` merges the delta into the
durable specs and files the change away.

### One change, one branch, one merge

This file names no trunk branch. Use the one the project treats as trunk.
Every change is delivered the same way, with no pull request and no review
that does not already exist.

1. Branch from trunk: `git switch -c change/<name>`.
2. Commit `plan` on the branch. The freeze diff and the approval record live
   there.
3. Apply, then commit `feat` and `chore: archive`. Squash the working commits
   into `feat`, so the branch carries exactly those three.
4. Push the branch and let the CI block run.
5. Merge only on a green status for the commit being merged. If trunk moved
   since the run, rebase the branch and run it again.
6. Merge without squashing: `git merge --no-ff change/<name>`. One push, one
   change, and the freeze diff survives.
7. Delete the branch. Tags are cut from trunk tips, never from a commit inside
   a change.

Trunk is never force-pushed and never receives a working commit. A branch is
yours to rewrite until it merges. The one commit made directly on trunk is a
release: it ships code that already merged and changes no behavior. Its shape is
under **Cutting a release**.

`scripts/check-change.sh` is the machine half of the gates. It checks that
`CHANGELOG.md` carries an `## Unreleased` heading, that every change folder
records a valid `x-level`, that L0 sets `skip_specs`, that an L2 or L3 proposal
links an ADR, that a durable spec carries no rendering detail, that every
scenario title appears in a test, that every `shortcut:` marker names an
upgrade trigger, and that a CI or Deploy block is either empty or complete.
`git config core.hooksPath .githooks` installs the gate once per clone.
`.githooks/pre-commit` runs the script before every commit, and
`.githooks/commit-msg` checks the trailers. That gate is local and always on.
`scripts/verify.sh` runs the same script and then the lint, build, and test
commands declared in Project facts. The hook runs the fast half only; add a new
project check to `verify.sh`, never to the hook.
A hosted runner is optional and declared in the CI section below.

After a change is proposed and its gate has passed, run the whole loop without
stopping to ask: apply, run the checks, update docs, archive, commit, push the
branch, merge, push trunk.
Pause only for a blocker, an ambiguity that would change the plan, a failing
check that needs a decision, or the next gate.

The routing table decides what the human reads. It never decides whether the
work is done.

### When a change does not ship

- **Abandoned.** Delete the branch and the change folder. Nothing archives, so
  nothing reaches the durable specs. When someone may ask why, leave one line in
  the handoff note or in the proposal of whatever replaces it. A branch that
  never merged leaves no trace on trunk, which is the point.
- **Waiting on another change.** A change that needs an unmerged change branches
  from that change's branch, not from trunk, and lands after it. Two changes
  that cannot merge in that order are one goal, not two changes. Never merge a
  branch whose parent is unmerged: trunk would lose the freeze commit the child
  depends on.

## Bootstrap: the first session

A copy is a template, not a project, until this section is done. `bootstrap`
owns it. The agent asks, then acts; the human answers and approves once.

The repository is still a template while any of these is true: **What this is**
holds the placeholder, Project facts are unfilled, or `adr/` has no accepted
decision. Once all three are false and the bootstrap change is archived, the
repository is a project and this section never applies again.

The agent does the setup a human would otherwise do by hand and reports each
step: check Node 22.12 and the OpenSpec version, ask before a global install,
`git init -b main` when there is no repository, and set
`git config core.hooksPath .githooks`. Those are reported, not silent. A remote,
a CI account, and deploy credentials stay the human's job.

Then the interview: ten topics in two batches. Product: what it does, who it is
for, what it is not, what data it handles, expected load. Machine: platform,
stack preference, where it runs, CI provider, where secrets live. Ten is the
ceiling, not the target. When the human says "you decide" or does not know, the
agent offers two or three options with a one-line tradeoff, picks one, and
records it as an assumption with a revisit trigger. It never fills a fact the
human did not give.

The bootstrap work is one L2 change with `skip_specs: true`, one gate, and the
answers as its artifact. The proposal carries `## Why`, `## What Changes`, and an
`## Answers` table. The gate is the page `node scripts/gate.mjs bootstrap`
opens: the product in their words, the stack with the rejected options, every
assumption, what will be created, and what is deferred. The ADR is the durable
record; the summary is what the human reads. Apply, verify, archive, and merge
in the same session.

What that change produces: the product README, **What this is**, Project facts,
the first `CONVENTIONS.md` entries, the ignore and editor files, the lockfile
policy, the stack ADR, and the CI and Deploy blocks when the human named a
provider. When they did not, both blocks stay empty and the project is local.

After this change the repository is a project. The next change is a normal
feature change, which is usually L1, and the human starts reading delta specs.

## Route the change before writing anything

Four questions. Answer each with evidence:

0. **Does observable behavior change?** Name the user-visible capability, the
   response, or the requirement that moves. Restyling or rewording that leaves
   every requirement as it was is not behavior.
1. **Can it be undone easily?** One commit, no data loss, no published contract.
2. **Can a machine prove it correct?** The check exists before apply: a test, a
   hook, or a visual diff that fails when the behavior is wrong. "A test could
   be written" is not an answer, or every change becomes L0. If a human is the
   only instrument that can tell, the answer is no.
3. **Does anything outside the change depend on it?** Name the document that
   holds the contract: a schema, an OpenAPI file, a permission model, a
   published API. If you cannot name one, either nothing depends on it or the
   contract is undocumented. The second case is its own L2 decision.

An unanswerable question means the change is not scoped enough to start.

The answers set the level. Take the highest level any one answer justifies, and
never pick a level to make the work smaller. L0 requires all four answers to be
benign.

| Level | Use when | What the change folder holds | Human reads |
|---|---|---|---|
| **L0** | all four answers are benign: one commit undoes it, a machine already proves it, nothing outside depends on it, and no observable behavior changes | proposal, tasks, `.openspec.yaml` with `skip_specs: true` and `x-level: L0` | nothing |
| **L1** | the product's observable behavior changes | proposal, delta spec, tasks, `design.md` when the approach is not obvious | the delta spec, before apply |
| **L2** | a contract, a stack choice, a dependency, or a capability boundary changes | an ADR first, then proposal, delta spec, design, tasks | the ADR, then the delta spec |
| **L3** | live data, someone else's data, or a published contract cannot be undone | everything in L2, plus rehearsal output, the executed rollback, and reconciliation counts | the evidence |

L0 is the default, not a reward. Examples: styling, copy, config wiring, tests, a
patch or minor dependency bump that keeps the API, refactors that keep behavior.
L2 examples: a new dependency, a major bump that changes an API, a new service,
an API schema change, a permission change. L3 examples: deleting
user data, changing a cryptographic scheme, publishing an API version that
cannot be retracted.

A change that is small per step but not undoable is not a decomposition, it is a
schedule. The level belongs to the feature; every step inherits it.

Record the level twice: `x-level` in
`openspec/changes/<change>/.openspec.yaml`, and the first line of the proposal.

## Big work

One change has one intent you can say in a single sentence, and one reason for a
human to look. Split into a goal when any of these is true:

- The "what changes" list needs "and also" more than once.
- It touches two capabilities that could ship independently.
- It needs two decisions of the same kind: two ADRs, two migrations, two
  permission models.
- Half the tasks could land and leave the product valid and useful without the
  other half.
- Its parts sit at different levels, for example an L0 copy change beside an L3
  migration. The higher level would put ceremony on the smaller part.

Do not split a single behavior spread over many mechanical edits. That is one
change with many tasks. Do not split when a child would leave the system invalid
and cannot be undone; redesign the step instead.

When the size is unclear, explore before proposing. Do not guess a split from
the title.

The split is provisional. The first child's proposal states the outcome and the
children you expect; later evidence can change the list. Each child must either
change observable behavior or leave the system valid while making the next step
safe.

- Pick a kebab-case goal slug, for example `offline-sync`.
- Create each child with
  `openspec new change <NN>-<name> --goal "<goal-slug>: <one line>"`.
- Order the child names `01-`, `02-`. OpenSpec sorts active changes by name, so
  the order is the landing order. Archive prefixes the date, which replaces the
  number as the sort key, so land the children in order and do not rebuild the
  sequence from the archive listing.
- The first child's proposal states the goal: the outcome, the shared contract,
  the children you expect, and what is out of scope. Later children link back
  to it and name their order.
- Each child must leave the system valid and ship on its own. Prefer expand and
  contract over a big step: add, dual-write, backfill, reconcile, switch reads,
  then remove.
- Route the goal once. Every child inherits its level. An irreversible step under
  an L2 goal makes the goal L3; it does not become a separate L2 child.
- Do not use `initiative:`. OpenSpec removed it and `--initiative` fails.
- There is no goal file. The group is rebuilt from the metadata and the names:
  `grep -rl 'offline-sync' openspec/changes --include='.openspec.yaml'`.

## Gates

- **L0.** Do not ask. Build, verify, archive, commit, push.
- **L1.** Open the gate page for the delta spec and wait for the submission. On
  approve, run the whole loop without stopping.
- **L2.** Open it for the ADR and wait. Then for the delta spec and wait. The
  spec must say what the ADR decided, nothing adjacent. After both approvals,
  run the loop.
- **L3.** Same as L2, then the rehearsal, the executed rollback, and the
  reconciliation. Apply only after approval of the evidence.

### How a gate is presented

Run `node scripts/gate.mjs <change>` and let it block. It renders the artifacts
the level needs into one page at `.tmp/gate/<change>-r<N>.json`, opens it, and
returns when the human clicks Approve or Request changes: exit 0 approved, 2
changes requested, 3 nobody answered. The conversation is where the human
reads. The repository is where the record lives. The page is generated from the
files, so the two cannot disagree.

When comments come back, revise the artifacts, bump `--rev`, and open a new
page. Never edit an approved artifact to match a comment; re-gate it.

`--static` writes the page and exits. Use it when the human is on another
machine, or when the agent cannot hold a shell open: they save the JSON by hand
and say so.

The page shows the markdown as it is, with a note box per file and nothing that
the artifacts do not say. An artifact that does not fit one screen is a change
too large for one change: split it rather than ask the human to scroll.

Approval is recorded in the repository, not in a chat window. As soon as the
human submits, add this block to `proposal.md` and make it part of the freeze
commit:

```markdown
## Approval

- Gate: L1 delta spec
- Approved by: <name>
- Approved at: YYYY-MM-DD
- Artifact: openspec/changes/<change>/specs/<capability>/spec.md sha256:<hash>
- Words: "<the human's message, quoted>"
```

Copy one `- Artifact:` line per file in the submission's `artifacts` list.
`tasks.md` is not in that list: the plan is on the page for the human to read,
but its checkboxes change while it is executed, and an approval that broke every
time a box was ticked would be a false alarm.

When the page came back with no comment, write `- Words: "(none)"`. The click is
the decision and the hashes are the evidence; do not invent a sentence for the
human.

The proposal's own hash covers its content outside the `## Approval` heading, so
recording the block does not change what it records. A recorded path written
before archive still names the file after the folder moves, so do not edit the
block to follow it. `node scripts/gate.mjs <change> --verify` recomputes every
hash, and `scripts/check-change.sh` fails when one moved: a spec edited after
its gate is a failed check, not a rumor.

After the gate the proposal is frozen: it is the record of what was approved.
Notes about how it went belong in the archive commit message, not in a section
added below the approval.

One block per gate, in the order they passed. A human merge is also a record. A
message in a chat window alone is not, because `git blame` cannot reach it.
Never write an approval the human did not give.

The freeze commit exists before the gate opens, so recording the approval
amends it rather than adding a commit after it:

```bash
git commit --amend --no-edit
```

Amend before apply writes anything. The diff of that amendment is the record:
the spec the human read and the block that says they approved it land in the
same commit, and if a line of the spec moved while the approval was added, the
diff shows it.

If apply proves the approved behavior wrong, stop and put the choice to the
human in one message: amend and re-gate at the same level, or ship what is
approved and open a follow-up change. Never edit an approved delta spec and
carry on. A re-gate adds a second block below the first, in order.

### When production is broken

Restore service first, route second. Revert to the last good version with the
Rollback command in the Deploy block, or turn off the flag. Write down what you
reverted, then route the fix at its normal level. An outage is not permission to
edit without a record, and it is not a reason to skip the failing signal and the
regression test. If the change cannot be reverted, the incident is L3 and uses
the L3 evidence.

If any routing answer changes mid-flight, stop and raise the level. Lowering a
level needs the human.

Before finishing any change, run `review-change`. If the change touches auth,
input, secrets, crypto, file paths, dependencies, or personal data, run its
security checklist. L2 and L3 also run `threat-model` before the design is
fixed. Then run `bash scripts/verify.sh`, which runs the checks and the declared
lint, build, and test commands, and report the exact commands and results.

## Specs

The durable spec in `openspec/specs/` is a product document. A product owner
reads it to decide what the system will do; a tester reads it to decide whether
it does. Write for both. The developer is not the primary audience: the code
and the change folder carry more detail than the spec ever should.

- Specs are organized by capability: `openspec/specs/<capability>/spec.md`.
  Extend the capability that owns the behavior. A change, ticket, endpoint, or
  story does not justify a new capability.
- Add a domain level (`<domain>/<capability>`) only when the flat list stops
  being scannable, and move capabilities in a dedicated change.
- A spec states observable behavior only. Functional and non-functional
  requirements live in the same file: privacy, accessibility, performance
  budgets, platform support, reliability, compatibility.
- No file paths, class names, function names, CSS values, library choices, or
  step-by-step plans. The test: if the implementation can change without the
  externally visible behavior changing, it does not belong in the spec.
- Technical detail belongs in the change: `proposal.md`, `design.md`,
  `tasks.md`. The change folder may be as technical as the work requires. The
  durable spec may not.
- One behavior per requirement. One `SHALL`/`MUST` per requirement. Every
  requirement has at least one scenario.
- A scenario title is a test name. The test that proves a scenario contains the
  scenario title, case-insensitive. Deleting a scenario deletes its test.
- A delta spec becomes the durable spec at archive, so write it behavior-first
  too. Put the implementation detail in `design.md`, not in the delta.
- `skip_specs: true` is for work that changes no behavior: refactors, tooling,
  docs, internal plumbing. The change still ships a proposal and tasks, and the
  proposal names the requirement the work leaves intact. An exemption leaves a
  record; an omission leaves nothing.
- Before archiving, run `scripts/check-change.sh`. It fails on a spec that
  carries rendering detail, which means the text describes rendering, not
  behavior. Rewrite it.

## Decisions

Durable decisions live in `adr/`, not in a change folder. The format is MADR:
Status, Date, Context, Decision, Consequences, Alternatives.

- L2 and L3 write the ADR before the proposal, so the decision is the first
  thing the human reads.
- A change that supersedes a decision writes a new ADR and links both. Never
  rewrite an accepted ADR.
- `design.md` is the change-local technical approach. It can disagree with the
  code next month. The ADR cannot.

## Keep it small

Take the first option that fully works:

1. Does it need to exist? Skip what nobody asked for.
2. Does the codebase already have it? Use it the way the surrounding code does.
3. Does the standard library or platform do it?
4. Does an installed dependency do it? Do not add one for a few lines.
5. Can it be one line a reader gets?
6. Otherwise, the minimum that works.

A new dependency is L2. Never cut validation, error handling, security, or
accessibility. A risky branch, loop, parser, money path, or security path gets
one small test. A known limit gets a `shortcut: <ceiling>, <when to upgrade>`
comment.

The level decides the process. This section decides the implementation inside
`apply`. Laziness never skips an artifact or a gate.

## Trace

Every commit except the initial template commit and a release commit carries the
change it belongs to and the level it was routed at:

```
feat: add the dark mode toggle

The app follows the system theme until the user picks one, then remembers
the choice.

OpenSpec-Change: add-dark-mode
OpenSpec-Level: L1
```

No commit carries a version. The version of a release is decided after QA, so a
commit cannot know it. It lives in a tag instead.

Commit shape:

```
plan: <what the change will do>       # L1 and above, the freeze commit
feat: <what the user can now do>      # code, tests, docs, changelog
chore: archive <change-name>          # synced specs, moved change folder
```

L0 folds `plan` into `feat`. The archive commit is always separate. The three
arrive on trunk together, in one merge and without a squash, so the freeze diff
survives on trunk and `git blame` still reaches the proposal.

A release adds a fourth shape, and it is the one commit made directly on trunk:

```
chore: release                        # trunk only, see Cutting a release
```

It belongs to no change, so it carries no trailers, and its message names no
version either. It changes no behavior, which is why it does not need a branch.
The trailer hook allows it by subject, and the invariant checks still run on it.

The freeze commit is what makes "the spec changed after approval" a diff
instead of a claim. Commit the artifacts before apply starts.

### The commits the trailer rule does not cover

A commit carries the change it belongs to, except for these, which the hook
allows on purpose:

- a merge commit, a revert, and a `fixup!` or `squash!` commit, because they
  carry someone else's message
- a `chore: release` commit, because it belongs to no change and changes no
  behavior
- the first commit of an empty history, because there is nothing to trace from
- rebuilding this template's root commit, because that commit carries no change
  at all. It is the only `--no-verify`, and it never happens in a project.

A line of code traces back through:

```
git blame -> commit -> OpenSpec-Change trailer
  -> openspec/changes/archive/<date>-<name>/proposal.md   (why)
  -> .../specs/<capability>/spec.md                       (behavior)
  -> adr/NNNN-<slug>.md or design.md                      (decision)
  -> git tag --contains <sha>                             (when it shipped)
```

A deferred limit is a `shortcut:` comment in the code. Before a release, list
the debt with `grep -rnE '(#|//) ?shortcut:' --exclude-dir=.git .`. A marker
with no upgrade trigger is a bug, not a decision.

## Versions and changelog

- A version belongs to a release, not to a repository or a commit. It is a tag,
  `<product>-v<semver>`, cut from the trunk tip after the candidate passed.
  Commits carry no version, because the final one is derived after QA and the
  commit cannot know it.
- `CHANGELOG.md` gets one entry per user-facing change, written for someone who
  does not read code, under `## Unreleased`. Name the change. Say what the user
  can now do. Do not list refactors, docs, or chores.
- The release renames `## Unreleased` to the version it ships and moves its
  entries under it, leaving a fresh empty `## Unreleased` above the new heading.
  The entry belongs to the change; the version belongs to the release.
- The artifact names itself: put the commit, the version, and the source into
  the image or package labels, so no separate deploy record is needed.
- The archive commit records what was verified. Name the commands and the
  result. "Tests pass" is not a record; `npm test: 128 passed` is.

### Cutting a release

The commands live in the Deploy block. The order does not change:

1. The candidate is green: the CI run for the commit being released passed.
2. Rename `## Unreleased` in `CHANGELOG.md` to `<product>-v<semver>`, and leave a
   fresh empty `## Unreleased` above it. The check refuses a changelog with no
   Unreleased heading, so the release commit has to leave one.
3. Commit that on trunk as `chore: release`. It ships code that already merged
   and changes no behavior, so it takes no branch and no trailers, and its
   message names no version. The file and the tag carry the version.
4. Run the Release command. It cuts `<product>-v<semver>` from that trunk tip,
   never from a commit inside a change.
5. Run the Deploy command.
6. Run the Smoke command. If smoke is red, run Rollback and route the incident
   at the level of what it cannot undo.

The deploy tool keeps the record: the image or package labels carry the commit,
the version, and the source. Nothing else has to be written down.

## Never without the human

- Deleting or rewriting user data, or a migration that cannot be reversed.
- Publishing an API version, changing a permission model, or rotating secrets.
- A new external dependency, a new service, or a new runtime (that is L2).
- Force-pushing a shared branch, rewriting published history, or deleting a
  repository.
- Adding, changing, or removing a skill.
- Changing the routing rules or a gate in this file.
- Installing a tool on the machine, such as a global `npm install`. Ask first.

## Files

- Scratch files, logs, dumps, and one-off scripts go in `.tmp/`. Never in the
  project root or beside source. A handoff note is the one file that stays there
  until the next session reads it, and it is deleted after that. A gate page and
  its submission are deleted when the change it belongs to is archived.
- A file that a tool can rebuild from the repository is not committed.
- Keep the repository readable by the human: `README.md` explains the product,
  `ARCHITECTURE.md` (once a container exists) explains the shape, `DESIGN.md`
  (when present) explains the visual language, `adr/` explains the decisions,
  and `CONVENTIONS.md` explains how the code is written.
- `openspec/config.yaml` holds the artifact rules and project context,
  `openspec/specs/` the behavior that already exists, and `REPO-FACTS.md` the
  confirmed operational facts and the rules for adding one.
- A rule has one owner. Behavior lives in `openspec/specs/`, a decision in
  `adr/`, a technical convention in `CONVENTIONS.md`, a confirmed fact in
  `REPO-FACTS.md`, and anything that changes routing or a gate in this file. A
  rule copied into two places drifts.
